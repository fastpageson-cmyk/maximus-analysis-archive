# 점포 단위 추천 v1 변경 사항

기준일: 2026-11-03 · 브랜치 `gunwoo/store-level`(`gunwoo/store-level`에서 분기)
규칙 모듈: `scripts/campus/서울캠/store_rules_v1.py` · 테스트: `tests/test_store_rules_v1.py`
로컬 실행: `docs/prompts/store_level_v1_local_run.md`

> 이 문서의 영향 숫자는 **v1 결과가 아니다.** 공개 v0 목록(`store_serendipity_top30_v0.csv`, `survey_cards_v0.csv`)에 새 규칙을 덧씌워 본 사전 추정이다. 원천(상가정보·인허가)과 점포 테이블은 로컬 Mac에만 있어서, 이 세션에서는 파이프라인을 다시 돌리지 못했다.

## 1. 무엇을 고쳤나

v0 상위 목록에서 문제 세 가지가 보였다.

| 문제 | v0 예시 | v1 규칙 |
|---|---|---|
| 찾아갈 곳이 아닌 가게가 "희소 업종"으로 올라옴 | 쇼핑 2위 출장열쇠집(철물/공구), 여가 1위 INTERNATIONALSPORTSREHAB, PC방 | 비목적지 제외(소분류 패턴 + 상호 키워드 + 경계 업종 스위치). 희소도 가점은 목적지형 소분류에만 준다 |
| 공부 목적이 너무 넓음 | 상위가 입시·교과학원, 미술학원, 댄스학원, 외국어학원, 문구점 | 점포 단계 공부 = 독서실/스터디 카페(+ 서점·북카페 스위치). 학원·문구는 목적 없음 |
| 업종 분류 오류 | 마이보쌈 → 일식, 상계솥뚜껑삼겹살 → 호프/통닭, 킹스컵밥 → 커피숍 | 상호 키워드 보정 > 인허가 위생업태(그룹이 다를 때) > 상가정보 소분류. `category_fixed`, `category_source` 열 |

상권 단계 정의(PATH-v0·SERP-v0의 `PURPOSE_INDUSTRIES`)는 바꾸지 않았다. 바뀐 건 점포 단계뿐이다.

## 2. 규칙 상세

모든 목록과 스위치는 `store_rules_v1.py` 상수다. 적용 순서는 `apply_rules()`: 업종 보정 → 점포 단계 목적 → 비목적지 제외 → 목적지형 여부.

### 2.1 업종 보정 (`resolve_category`)

우선순위: **상호 키워드(name_rule) > 인허가 위생업태(license) > 상가정보 소분류(sbiz)**.

1. **인허가 위생업태 우선.** 상가정보 음식 점포에 매칭된 위생업태가 `LICENSE_TO_SERVICE`로 옮겨지고, 그 서비스업종의 그룹(식사 / 주점 / 카페 / 제과, `SERVICE_GROUP`)이 상가정보 쪽과 다르면 위생업태를 쓴다. 예: 상가정보 '카페'인데 위생업태가 '호프/통닭'이면 주점(식사)으로 본다.
   - 식사 안(한식 ↔ 일식 등)에서는 바꾸지 않는다. 인허가 위생업태는 '한식'으로 일단 등록하는 경우가 많아서, 바꾸면 더 틀린다. `LICENSE_OVERRIDE_WITHIN_MEAL = True`로 켤 수 있다.
2. **상호 키워드 보정(`NAME_RULES`).** 음식 업종(상가정보 I2 소분류, license_only)에서만 쓴다. 위에서부터 처음 맞는 규칙 하나를 적용한다. **현재 서비스업종이 규칙과 이미 같으면 그대로 둔다**(예: '국/탕/찌개류'의 '갈비탕'은 한식이라 안 바뀐다). 보정 소분류명은 상가정보 소분류명을 그대로 써서, 희소도와 MMR이 같은 소분류로 묶인다.

| 상호 키워드 | 보정 소분류명 | 서비스업종 → 목적 |
|---|---|---|
| 스터디카페, 독서실 (전 업종) | 독서실/스터디 카페 | 독서실 → 공부 |
| 컵밥, 김밥, 떡볶이, 분식 | 김밥/만두/분식 | 분식전문점 → 식사 |
| 족발, 보쌈 | 족발/보쌈 | 한식 → 식사 |
| 곱창, 막창, 대창 | 곱창 전골/구이 | 한식 |
| 닭갈비, 닭발, 오리고기·오리구이, 닭한마리 | 닭/오리고기 구이/찜 | 한식 |
| 치킨, 통닭 | 치킨 | 치킨전문점 |
| 한우, 소고기, 소갈비, 우대갈비 | 소고기 구이/찜 | 한식 |
| 삼겹, 오겹, 목살, 숯불, 갈비, 고깃집 | 돼지고기 구이/찜 | 한식 |
| 라멘, 우동, 소바 | 일식 면 요리 | 일식 |
| 초밥, 스시, 사시미 | 일식 회/초밥 | 일식 |
| 짜장, 짬뽕, 마라탕, 반점, 중화요리 | 중국집 | 중식 |
| 호프, 포차, 이자카야, 주점, 맥주 | 생맥주 전문 | 호프-간이주점 → 식사 |
| 다방, 커피, 카페, COFFEE, CAFE | 카페 | 커피-음료 → 카페 |

- 오탐이 잦은 키워드는 뺐다: '라면'(분식집), '순대'(순대국은 한식), '만두'(중식 만두), '등심'(돈가스), '돼지'(흑돼지 돈카츠), '국수'(분식 ↔ 한식, 목적 차이 없음).
- 결과 열: `소분류명`(보정값), `소분류명_원`(원래 값), `category_fixed`(바뀌었는지), `category_source`(sbiz / license / name_rule). license_only 점포는 바뀌지 않아도 `license`다.
- 보정 뒤 목적도 다시 정한다. 킹스컵밥은 카페 → 식사, 상가정보 '카페'인 밀물호프는 카페 → 식사.

### 2.2 점포 단계 공부 (`store_purpose`)

| 서비스업종 | 상권 단계(PATH-v0) | 점포 단계 v0 | 점포 단계 v1 |
|---|---|---|---|
| 독서실(독서실/스터디 카페) | 공부 | 공부 | **공부(핵심)** |
| 서적(서점) | 공부 | 공부 | 공부. `STUDY_INCLUDE_BOOKS=False`면 목적 없음 |
| 상호에 북카페·책방이 든 카페 | 카페 | 카페 | 공부. 스위치가 꺼지면 카페 |
| 일반교습학원·외국어학원·컴퓨터학원·예술학원 | 공부 | 공부 | 목적 없음 |
| 문구, 비디오/서적임대 | 공부 | 공부 | 목적 없음 |
| 스포츠강습(태권도·필라테스) | 공부 | 목적 없음 | 목적 없음 |

- v0의 `NO_PURPOSE_SERVICES = {"스포츠강습"}`과 같은 방식으로 `NO_PURPOSE_SERVICES_V1`에 학원·문구를 더했다.
- 근거: 동대문구 대학생이 "공부하러 30분을 이동"할 때 가는 곳은 독서실·스터디카페·서점·북카페다. 학원은 등록해야 다니는 곳이고, 문구점은 공부하러 가는 곳이 아니라 물건을 사러 가는 곳이다.
- **공부하기 좋은 일반 카페는 아직 넣지 않는다.** 리뷰 키워드('오래 머물기·공부' 테마)가 생겨야 고를 수 있다. 네이버 키워드 집계가 막힌 지금 상호만으로 고르면 오탐이 많다. 리뷰 데이터가 생긴 뒤(v2) 다룬다.

### 2.3 비목적지 제외 (`exclude_reason`)

다음 셋 중 하나에 걸리면 `목적`을 비우고 `exclude_reason`에 사유를 남긴다. 제외 전 목적은 `목적_보정전`에 남는다.

- **(a) 소분류 패턴 `EXCLUDE_SUBTYPE_PATTERNS`**(소분류명 부분 일치): 철물, 공구, 열쇠, 수리, 설치, 부동산, 중개, 세탁, 빨래, 렌탈, 임대, 대여, 약국, 의원, 병원, 치과, 한의, 재활, 치료, 요양, 장례, 벽지/장판, 자동차, 주유, 인력, 이삿짐, 청소 서비스, 방역, 인쇄 → `subtype`
  - 공개 v0 목록에서 실제로 걸린 소분류: 철물/공구 소매업, 벽지/장판/마루 소매업, 약국. 나머지(부동산·의원·세탁 등)는 v0에서도 목적 대응표에 없어 빈칸이었지만, 대응표가 바뀌어도 막히도록 같이 둔다.
- **(b) 상호 키워드 `EXCLUDE_NAME_KEYWORDS`**(대소문자 무시): 출장, 수리, 설치, 열쇠, 도어락, 대행, 렌탈, 재활, 치료, 클리닉, REHAB, 통증, 정형외과, 의원, 한의원, 병원, 약국, 부동산, 공인중개, 세탁, 도배, 철거, 용달, 퀵서비스 → `name`
  - '청소'(청소년), '수선'(수선화), '이사'(이사벨)는 오탐 때문에 넣지 않았다.
- **(c) 경계 업종 `BOUNDARY_SUBTYPES`**: 소분류명마다 (유지 여부, 근거). False면 `boundary:<소분류명>`.

| 소분류 | 기본 | 근거 |
|---|---|---|
| PC방 | **제외** | 게임 목적이면 집 근처 PC방과 다를 게 없어 거기까지 가 볼 이유가 약하다 |
| 노래방 | **유지** | 친구와 함께 가는 여가로 상권 나들이의 마무리가 된다. 코인노래방도 대학생 이용이 많다 |
| 여관/모텔 | 제외 | 숙박 업종. 30분 안 당일 나들이 추천에 맞지 않는다 |
| 호텔/리조트 | 제외 | 숙박 업종. 라운지·카페가 따로 있으면 카페 업종으로 잡힌다 |
| 헬스장 | 제외 | 회원제 운동 시설. 한 번 찾아가는 곳이 아니다 |
| 전자 게임장 | 유지 | 오락실은 들러 볼 만한 놀거리다 |
| 기타 오락장 | 유지 | 뽑기방·방탈출 등 체험형 놀거리가 섞여 있다 |
| 당구장 · 볼링장 · 탁구장 · 스쿼시/라켓볼장 | 유지 | 친구와 함께 하는 체험형 여가 |
| 골프 연습장 | 유지 | 스크린골프는 모임 여가로 쓰인다(레슨 아카데미가 섞이는 건 한계) |
| 종합 스포츠시설 · 기타 스포츠시설 운영업 | 유지 | 클라이밍 등 체험형이 섞여 있다. 재활·치료는 상호 키워드로 뺀다 |

바꾸려면 `BOUNDARY_SUBTYPES["PC방"] = (True, "...")`처럼 첫 값만 바꾼다. PC방·노래방 외 숙박·헬스장 제외는 이번에 추가한 판단이라 팀 확인이 필요하다.

### 2.4 희소도 가점은 목적지형에만 (`is_destination`)

- 생활형 소분류(`ERRAND_SUBTYPE_PATTERNS`): 슈퍼마켓, 편의점, 정육, 수산물, 반찬/식료품, 채소/과일, 건어물, 미곡, 곡물, 식료품, 핸드폰, 가전, 전기용품, 조명, 실/섬유, 침구, 커튼, 가구, 안경.
- 목적(쇼핑)은 남기되 `rarity = 0`이다. 점수의 희소도 항(0.3)이 빠지고, "이 상권에 드문 ○○" 이유와 '희소 업종' 공공 태그도 붙지 않는다. 원래 값은 `rarity_raw`에 남긴다.
- 그 밖의 소분류(음식·카페·의류·한복·잡화·꽃·악기·서점·스터디카페·여가 등)는 목적지형이다.
- 희소도 묶음 기준이 v0의 소분류코드에서 v1은 **보정된 소분류명**으로 바뀐다. 업종 보정된 가게가 같은 소분류로 함께 묶이게 하려는 것이다.

## 3. 사전 영향 추정 (v0 목록 기준, v1 결과 아님)

`scripts/store_level/estimate_store_rules_v1_impact.py`를 공개 v0 CSV에 돌렸다. 가게별 판정: `data/processed/store_level/store_rules_v1_preimpact_top30.csv`, `store_rules_v1_preimpact_cards.csv`.

추정의 한계:
- 공개 CSV에는 소분류코드와 매칭 위생업태가 없다. 소분류명 → 서비스업종은 스크립트 안 `NAME_TO_SERVICE`로 옮겼고, **인허가 위생업태 우선 규칙은 적용하지 못했다.**
- 빠진 자리를 v1에서 어떤 가게가 채우는지는 알 수 없다. 목적별 추천 수는 상권 안 후보가 남아 있으면 다시 30곳 가까이 찬다.
- '희소 가점 상실'은 목록에 남지만 점수가 크게 떨어져(희소도가 사실상 유일한 차별 항) v1에서는 대부분 밀려날 가능성이 높다.

## 5. 남은 한계

- **상호 키워드 규칙은 사람이 정했다.** 오탐(예: '숯불' 들어간 장어집 → 돼지고기 구이/찜, 한식 안에서만 바뀌어 목적 영향은 없음)과 미탐이 있다. 로컬에서 `category_fixed=True` 표본을 뽑아 검수해야 한다.
- 위생업태 우선 규칙은 그룹이 다를 때만 쓴다. 상가정보 '한식'인데 실제로 일식인 가게는 상호 키워드가 없으면 그대로 남는다.
- 비목적지 목록은 공개 v0 목록에서 보인 사례 중심이다. 전체 테이블의 `exclude_reason` 분포와 목적별 남은 소분류를 로컬에서 확인해야 한다.
- 경계 업종 판단(숙박·헬스장 제외)은 팀 합의 전이다. 골프 연습장 안 레슨 전용 아카데미는 구분하지 못한다.
- 서점·북카페를 켜도 공부 후보가 적다. 상권당 3곳을 못 채우는 상권이 늘어 공부 추천 수가 v0(25)보다 줄 수 있다.
- 공부하기 좋은 일반 카페, 리뷰 기반 테마는 키워드 집계가 생긴 뒤로 미룬다(v0와 같은 이유: 캡차 토큰 없이는 429).
- 이 문서의 영향 숫자는 v0 목록 위의 추정이다. 실제 v1 숫자는 로컬 실행 뒤 `store_serendipity_v0_v1_compare.md`로 확인한다.
